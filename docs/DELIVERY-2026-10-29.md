## Nouveautés disponibles

1. **Matériel des activités :** modifier directement le libellé et la quantité, puis sauvegarder ; l'API vérifie l'appartenance à l'activité et les droits du compte.
2. **Éditeur de description enrichie :** modification directe avec gras, italique, souligné, titres, listes ordonnées et à puces ; collage en texte brut ; le HTML stocké est nettoyé par `ammonia` avant affichage. Les anciens textes restent valables. Les fiches imprimables récupèrent le HTML enrichi.
3. **Inscription :** déjà proposée depuis l'écran de connexion ; les comptes créés deviennent `user` (lecture seule). Les personnes autorisées rattachent ensuite le compte à un club ou une équipe.
4. **Logs :** `tracing` dans l'API et table SQLite `audit_events` pour les requêtes authentifiées qui modifient des données. `/audit` affiche les 100 derniers événements pour les administrateurs. Ni les mots de passe ni les corps HTTP ne sont enregistrés.
5. **Ordre des activités :** glisser-déposer dans la préparation d'une séance, avec boutons ↑/↓ utilisables sur mobile ; persistance transactionnelle et validation de la liste complète d'identifiants.
6. **Sessions :** JWT local de 7 jours au lieu de 24 h. Une réponse 401 à une requête authentifiée nettoie le stockage et redirige vers `/login` ; un 403 n'entraîne pas de déconnexion.
7. **Rôles et équipes :** `visitor` public non connecté, `user` lecture seule, `trainer` écriture sur ses équipes, `manager` sur ses clubs, `administrator` partout. Les rôles globaux et les rattachements d'équipes/clubs sont vérifiés côté API. Une séance peut appartenir à une équipe ; la liste et les modifications sont filtrées, les anciennes séances privées restent accessibles à leur créateur. Les joueuses et activités peuvent être rattachées à une équipe. Les clubs ne sont publics qu'après publication explicite.
8. **Tableau tactique intégré :** `/tactics` fournit une première version autonome : terrains football, volleyball ou neutre, symboles déplaçables, flèches, sauvegarde de schémas et contrôles serveur sur les objets. Il s'agit d'une V1 de l'outil de dessin et non d'un clone complet d'easy2coach.

## Préparation locale indispensable

**Sauvegarder d'abord le fichier `api/data/seppyl.local.db`** (ou `data/seppyl.local.db` selon le répertoire de travail). Le démarrage synchronise le schéma et crée plusieurs tables/champs. Ne pas lancer cette branche directement sur la base de production.

Créer une branche locale en suivant la branche distante, puis exécuter l'API et le client comme d'habitude :

```powershell
git fetch origin
git switch --track origin/feat/clubs-roles-editor
# Dans le répertoire qui contient la base SQLite :
cargo run -p api
# Dans un autre terminal :
cd client
dx serve --platform web
```

Pour attribuer explicitement le rôle Administrateur à un compte **existant**, lancer l'API avec la variable d'environnement `SEPPYL_BOOTSTRAP_ADMIN_USERNAME` définie sur son identifiant (PowerShell : `$env:SEPPYL_BOOTSTRAP_ADMIN_USERNAME="admin"`). Le compte doit exister au démarrage. La variable est une opération privilégiée côté serveur ; ne pas l'exposer dans le client. Enlever la variable après l'initialisation et vérifier `GET /account`.

Configurer `JWT_SECRET` avec une valeur forte et unique avant toute exposition externe. Le serveur de développement ne doit pas être publié tel quel. Le JWT est temporairement conservé dans le stockage local du navigateur : passer aux cookies sécurisés et au SSO/OIDC avant une mise en production de cette refonte.

## Scénarios à valider manuellement

- Avec un compte administrateur, créer un club et une équipe, attribuer un entraîneur et un utilisateur en lecture seule.
- Vérifier que l'entraîneur peut créer une séance **avec équipe**, y rattacher des joueuses et des activités, puis les retrouver depuis un second compte de la même équipe.
- Vérifier qu'un compte lecteur voit la séance mais reçoit 403/404 pour la modifier, et qu'un utilisateur d'un autre club n'en voit aucune donnée.
- Activer puis désactiver la visibilité publique d'un club et consulter `/public` sans connexion. Les joueuses et entraînements ne doivent pas apparaître publiquement.
- Modifier le nom et la quantité d'un matériel existant ; vérifier l'agrégation dans la séance et la fiche PDF.
- Mettre en forme une activité, quitter puis réouvrir l'édition, et tester les titres/listes dans la fiche imprimable.
- Réorganiser 3 activités par glisser-déposer puis par ↑/↓, recharger la page, vérifier que le PDF conserve l'ordre.
- Forcer un JWT expiré, tenter la création d'une joueuse : redirection automatique vers `/login`. Une erreur 403 de droits ne doit PAS provoquer cette redirection.
- Ajouter une joueuse à l'effectif d'une équipe et contrôler sa présence dans la séance associée.
- Créer un schéma tactique, déplacer des symboles, tracer une flèche, sauvegarder, recharger, modifier et supprimer.
- Consulter le journal d'audit avec un administrateur, puis vérifier le refus avec un compte ordinaire.
- Tester au minimum une fois sur smartphone, tablette et ordinateur.

## Points restant à approfondir après retour utilisateur

- Gestion de sessions révoquables et SSO Donnarieix/OIDC.
- Éditeur de texte complet type Google Docs (annulation/refaire élaborés, tableaux, collaboration et commentaires).
- Tableau tactique multiphase, dossiers, templates, exports SVG/PDF, insertion directe des schémas dans les activités ; la V1 actuelle reste un éditeur de schémas séparé.
- Parcours d'administration avancé : invitations, recherche de comptes, suppression de rôles, groupes et droits granulaires.
- Simplifier l'UX du rôle lecture seule : certains formulaires peuvent rester affichés, mais l'API bloque effectivement les modifications.
- Migrations SQL versionnées et vrai plan de rollback des schémas plutôt que la seule synchronisation automatique ; les tags Git ne restaurent pas une base de données modifiée.

En cas de retour arrière, restaurer **aussi une sauvegarde compatible de la base SQLite**. Revenir au code d'un tag ne suffit pas à annuler les changements de schéma.
